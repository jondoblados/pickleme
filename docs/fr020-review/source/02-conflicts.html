All or nothing. A hold covers every requested slot or none of them. A partial success never takes some courts without telling the organiser.
Who wins. The database enforces one active hold or booking per court and time. The first transaction to commit wins; the second gets slot_unavailable with the clashing slots.
Alternatives. Worked out on the server from the same availability query: the slots that are still free, the same courts at the next free time, or the same times on the nearest other day.
Retries are safe. Each hold request carries an idempotency key, so a double tap or a flaky connection never creates two holds.
Expired holds. Released automatically by a scheduled job and also ignored by the availability check once past their expiry, so a stuck hold can't block a court.
Slot watch (optional). Organisers can ask to be emailed when a taken slot is released. No automatic booking.
